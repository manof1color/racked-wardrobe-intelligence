# Security policy

## Supported scope

The competition demo is an educational prototype. Security reports should cover authentication/session integrity, role authorization, consent bypass, exposure of raw wardrobe data, unsafe uploads, secret leakage, and cohort-threshold bypass.

## Never include in an issue

Do not publish any password — including synthetic test-cohort credentials, which are shared with judges privately and never committed to this repository — or session cookies, AWS credentials, model/API keys, private user data, or exploit output containing sensitive data. Share a minimal redacted reproduction with the repository owner privately.

## Baseline controls

- Secrets come from ignored runtime environment files or the deployment platform.
- `main` is protected: every change arrives by pull request, and `verify`, `accessibility` and CodeQL (`Analyze JavaScript and TypeScript`) must pass; force pushes and deletion are blocked (read back from GitHub's public API on 2026-11-01). Check it: `gh api repos/manof1color/racked-wardrobe-intelligence/branches/main --jq .protected`, or `pnpm verify:live`.
- Sessions are signed, HTTP-only, SameSite, expiring cookies.
- Passwords are hashed with scrypt and a unique 18-byte random salt (`lib/password-hash.ts`). Every check verifies both Node's default cost (N = 2^14) and OWASP's minimum (N = 2^17, r = 8, p = 1), doing the same derivation work whether or not the email has an account. **Rolled out in two steps:** this release keeps writing the default cost, so a rollback can read every hash; setting `RACKED_PASSWORD_SCHEME=scrypt-n17` then writes new hashes at N = 2^17 and replaces old ones on their owner's next sign-in.
- A known-device cookie uses a separate sign-in budget shared by all known devices for the email. Password changes invalidate older cookies.
- Brand accounts can turn on two-step sign-in with any standard authenticator app (TOTP, RFC 6238; `lib/two-step.ts`). It adds no running cost: no text messages, no email, no new AWS service. Turning it on, getting new recovery codes and turning it off each need a current code, and setup and turning off also need the password, so a stolen session cookie cannot attach or remove an authenticator. The secret is stored sealed with AES-256-GCM under a key derived from `SESSION_SECRET` and bound to its account; each code works once; recovery codes are stored only as hashes and each works once. The right password alone earns a five-minute challenge, signed for that purpose only, never a session. Every code tried counts against the account — five per fifteen minutes across all servers — before it is checked, failing closed, and a wrong code after a right password appears in the owner's activity log.
- Consumer/Brand pages enforce roles on the server.
- A brand registered since 2026-10-27 starts pending and can use no brand capability until the owner approves it; the owner can also revoke a brand, which takes its products out of the public registry. Every brand route makes the same check first (`lib/server/brand-access.ts`). Brands from before that keep working with no migration. Approval is a manual owner step for now (`docs/brand-approval.md`).
- A brand may enroll at most 300 products. The limit is checked before any photo is read and enforced in the same DynamoDB transaction that saves the product, so requests sent at once cannot pass it.
- Racked takes no real payments. The only payment step is Stripe test mode on fictional products (`lib/test-checkout.ts`): only a Stripe test key is accepted, a reply that does not confirm test mode is refused, a real or pilot brand's product is refused before Stripe is called, the server sets the price, and card details are typed on Stripe's page and never reach Racked.
- Consumer analysis requires explicit consent.
- Every change to brand sharing is written together with a permanent record of it — on or off, when, and the version of the wording on screen — in one DynamoDB transaction, so the setting never changes without its record (`lib/brand-sharing-consent.ts`). Each wording is pinned to its version by test. The record is deleted with the account.
- Brand-safe aggregate helpers suppress cohorts below 25 and strip identity/raw-wardrobe fields.
- A DynamoDB-backed enumeration budget caps how many distinct products one brand account can pull aggregates for in a rolling window, on the production dashboard and Hanger paths.
- Sliding-window rate limits protect sign-in, registration, garment analysis, both Hanger agents, brand metrics, community publishing/likes, and every account write — wears, outfits, garments, consent, brand enrollment and Looks — with 429 responses. Counters are in-memory per compute instance — a deliberate zero-cost first layer, not a WAF replacement. Their per-client key is the `X-Forwarded-For` entry the platform appended, never one the client wrote.
- Shared limits in DynamoDB hold across every instance, keyed by HMAC so no email or account ID is stored in a key: 8 password-check slots per email per 15 minutes in each device class, refunded for correct passwords, 100 sign-ups per hour site-wide, 3 reset emails per address per hour, and, per client address across every instance, 30 sign-in attempts per 5 minutes, 20 sign-ups per hour and 10 reset requests per hour — set above the per-instance limits, so one venue's shared Wi-Fi is not locked out. Requests with no readable address share a budget per action. They fail **open** if DynamoDB is unreachable (the per-instance layer still applies). A signed known-device cookie, issued on sign-in and on a completed reset, exempts its browser from that email's pause, so a stranger's wrong guesses cannot lock the owner out.
- AI budgets: per account per day in requests, and site-wide per day in Bedrock model calls (default 1,500, `AI_DAILY_CEILING`), each model call metered — including every agent round. They fail **closed**: an unreadable counter means no model call and the non-model fallback.
- Sign-up and password-reset forms carry a bot trap: a honeypot field and an HMAC-signed, timestamped form token.
- Each account sees its own security activity (sign-ins, failed attempts on its email, password and detail changes) for 90 days, with a coarse device label and no IP address, and can sign out every other device. Only the owner's session can read it. Entries past 90 days are dropped when the log is read, from the same query, because DynamoDB's time-to-live deletes in the background and can lag by days.
- A demo session never sees a real activity log. The demo brand is one shared account, so its real log is every judge's sign-ins and every failed attempt on its address; `/api/account/activity` answers a demo session with a fixed, made-up log and never reads the store. Its Settings is a preview with every control disabled, and no authenticator secret is stored on it.
- The demo brand may use Fill in from photo, which stores nothing; enrolling, editing and retiring stay refused. Each demo session's readings and Brand Hanger questions are counted under its own session key (12 readings and 30 questions a day), not the shared account, so one visitor cannot use up the next one's.
- Demos may use at most 80% of the day's AI model calls (`DEMO_SITE_CALL_SHARE`). A demo's call is counted against the demos' own counter first and refused once that is spent, without touching the shared one, so however many demos are opened, real brands and consumers keep the rest. Every demo of any kind counts toward the 120-an-hour site-wide demo ceiling.
- The four seeded judge accounts are shared, so they can only ever be opened as a demo. A password sign-in to one opens the matching demo instead; a full session to one is refused (`lib/session.ts`); and the store refuses to change their email or password, sign out their sessions, delete them, or start two-step on them.
- A New Brand demo is a private brand with no email, password or brand-name claim. Its products are never written to the product registry, so they cannot answer a real person's label, a search, a public page or a Community card; it may enrol up to 5 and never publish a Look; and its records and photos expire within two days.
- Every response carries browser security headers (HSTS, `nosniff`, `X-Frame-Options: DENY`, referrer and permissions policies).
- Every page carries an **enforced** Content Security Policy with a fresh nonce per request (`middleware.ts`, `lib/content-security-policy.ts`): `script-src 'self' 'nonce-…' 'strict-dynamic'`, with no `'unsafe-inline'` or `'unsafe-eval'` in production. Next.js puts the nonce on its own scripts, and the root layout puts it on the install-prompt capture. An injected inline script or event handler does not run, and each violation is reported to `/api/security/csp-report`. Photos may load only from the upload bucket's own host (`https://<bucket>.s3.<region>.amazonaws.com`, the host the presigner signs), falling back to `*.amazonaws.com` only when the bucket is unknown or not a plain DNS name. `RACKED_CSP_MODE=report` turns it back to report-only without a code change (a redeploy is needed for the setting to reach the runtime). Enforced on the live site since 2026-11-03, after a live check in report-only mode found no violations from Racked's own code; the owner's read-back is recorded in `docs/security-verification.md`.
- State-changing API requests must carry an Origin on the explicit allowlist in `lib/site-origin.ts`; a request's own Host or X-Forwarded-Host grants no trust. Password-reset links use the configured public origin only.
- Request bodies are capped by declared length in middleware and by bytes actually read in the photo routes.
- The account record behind every session, role, and two-step check, and the profiles read to decide consent for a brand aggregate, are read strongly consistent, so signing out everywhere, deleting an account, or withdrawing consent takes effect on the next request.
- The in-memory limiter stays within 10,000 keys by dropping the least recently used one, never by clearing every counter, so a flood of new keys cannot reset the budget of a key in use.
- A brand enrollment stores every photo or keeps none: if an upload or the record write fails, the photos already stored are deleted.
- Public community responses are rebuilt from an explicit allowlist so owner account IDs, private S3 keys, and database key attributes never leave the server.
- Uploads are private, type-allowlisted, size-limited, and decoded at no more than 64 megapixels. Brand product photos are re-encoded without location or camera metadata before storage. **There is no malware scanning**: decoding and re-encoding proves a file is an image, which is not the same thing.
- Request bodies are validated at runtime (`lib/request-input.ts`): JSON objects only, read under the cap; IDs in Racked's own shapes; lists checked whole before any item is used; fields that name an owner, a role, or a verification state refused, not ignored. Identity and ownership always come from the session, and every referenced garment, outfit, and product is checked in the session's own partition.
- Failures are answered one way (`lib/api-errors.ts`): a refusal's own words, or a generic message with a short reference. Logs carry that reference, the error's name, and its HTTP status — never its message, the request body, an email, or an IP address.
- Wear recording is one DynamoDB transaction, idempotent on a client `requestId` and on the same pieces within ten minutes, so retries and double taps cannot inflate metrics and a partial failure leaves nothing half-counted.
- Released brand aggregates withhold every figure that could describe fewer than five owners, release the latest wear as a day, and the enumeration budget is claimed atomically.
- Logs must exclude tokens, raw images, credentials, and personal data.

## Still open

Three pilot brands have created accounts and uploaded products on the live app, so these are live gaps rather than pre-launch tasks:

- **Inline styles are still allowed.** The Content Security Policy keeps `style-src 'unsafe-inline'`: React writes style attributes throughout the app. Injected CSS cannot run script, but it can restyle a page; removing it means moving those styles into classes.
- **Edge rate limiting (AWS WAF).** Per-address limits belong at the edge, where the real client address is known. **Deliberately not bought:** AWS WAF adds a recurring charge, and the project avoids new recurring spend. Until then the per-address limits in the app, shared across servers through DynamoDB, are the control.
- **Upload malware scanning** is not implemented. Every stored photo is a fresh encoding made by `sharp` from decoded pixels, not the uploaded file, which removes payloads hidden in the file; the remaining risk is a flaw in the image decoder itself, which is why `sharp` is kept current. **Deliberately not bought:** a scanning service adds a recurring charge.
- **Brand approval is manual.** The owner checks each new brand by hand (`docs/brand-approval.md`). An automated waiting period and business verification are planned after the competition. A pending account reserves its brand name for 14 days (`BRAND_PENDING_CLAIM_DAYS`); after that another registration may take the name and the stale account is revoked.
- **No email verification at sign-up (decided: not now).** A new account gets a session immediately. Sign-ups are capped site-wide and per address, every AI cost is capped per account and site-wide, and a new brand can store nothing until it is approved.
- **Choices made under the earlier sharing wording.** Every change since 2026-10-27 is recorded with the wording version shown, but an account that turned sharing on before then has no record and reads as the earlier wording (`before-2026-10-27`), which did not say earlier wear is included. Whether to ask those accounts to confirm again is an owner decision.
- **CloudFormation changes** in `infra/template.yaml` must be applied and verified against the live stack; the template is not proof of live settings. In particular, **DynamoDB time-to-live on `ttl` was switched on and read back as ENABLED on 2026-11-01** (`pnpm verify:aws`; it had drifted from the template and read DISABLED on 2026-10-30). Rate-limit windows, reset tokens, activity entries and demo copies now expire on their own; DynamoDB deletes them in the background, usually within days, so the code still checks expiry where it matters.
- **Strong password cost: switched on 2026-10-30.** `RACKED_PASSWORD_SCHEME=scrypt-n17` is set in Amplify (read back from the app's settings; the latest Amplify build, 176, succeeded). New passwords are hashed at N = 2^17 and each older hash is replaced the next time its owner signs in, so accounts that have not signed in since still hold the older cost. Roll back no further than a release that reads both schemes.
- **Two-step sign-in and `SESSION_SECRET`.** Authenticator secrets are sealed under a key derived from `SESSION_SECRET`. Replacing that secret signs everyone out, as before, and also makes every enrolled authenticator unreadable: brands then sign in with a recovery code and set up two-step sign-in again. Recovery codes do not depend on it. A brand that has lost both its phone and its recovery codes can only be helped by the owner removing the `twoStep*` attributes from its profile after confirming who they are outside the app. It is optional and offered to brand accounts only; the shared DEMO accounts judges sign into cannot turn it on, so no one can lock the others out.
- **Shared limits fall back to per-instance limits for sign-in.** A DynamoDB outage leaves only a per-instance layer against password guessing: each server instance allows eight attempts per email per window, so the real total scales with the number of warm instances. Sign-up and reset limits still fail open.
- **Consent history (decided: keep, and say so).** Turning brand sharing on includes wear recorded *before* opting in. The owner kept this behaviour; the sharing switch, the scan review, and the Privacy page now say so.
- **Scan photo expiry depends on the live bucket rule.** Unkept scan photos wait under `temp/` and are deleted by the `DeleteTemporaryUploads` lifecycle rule. Verified present and enabled on the live bucket on 2026-10-30 (one-day expiry on `temp/`). If the rule were missing, they would stay until account deletion; check it with the command in `docs/security-verification.md`. Photos left by scans before this change are not touched.
- **Differencing over time.** A brand that re-opens a released product can watch exact totals change; small cells are withheld, but no noise is added. Differential privacy would close this; it is not implemented.
- **Authorization tests** run against a local production build with synthetic accounts and a local DynamoDB (`docs/security-verification.md`); they have not been run against the live site, which needs real sign-ins.

A whole-codebase review with Cloudflare's open-source [security-audit skill](https://github.com/cloudflare/security-audit-skill) ran on 2026-11-02; the fixes merged in #211, #214, #215 and #216. Its report is kept private because this repository is public. Automated repository checks currently include production dependency auditing on every change, weekly Dependabot version updates, and CodeQL scanning on pushes, pull requests, and a weekly schedule. These checks complement rather than replace manual authorization and privacy review.
- **Community metrics window.** Brand Community metrics use at most 1,000 recent event rows. High volumes of anonymous events can push older activity out of that window.
