## Phase 24 — Garment cropping that follows the piece (2026-08-29)

- [#95](https://github.com/manof1color/racked-wardrobe-intelligence/pull/95) fixes the reported defect that garment pieces were not being cropped correctly. Two causes were measured rather than guessed. The three-view display crop relied on sharp's border trim, which needs a near-uniform frame edge and therefore failed on carpet, wooden flooring, and one-window lighting — the backdrops people actually photograph against. The look-scan cutout removed the backdrop well but then took bounds over every remaining opaque pixel, so a pillow beside the garment or the neighbours on a crowded rail dragged the crop wide. A new silhouette pass removes the backdrop and then keeps only the largest connected region, so the crop follows the piece instead of the frame's leftovers. `scripts/crop-benchmark.ts` scores every approach by intersection-over-union against a known garment rectangle across 14 seeded backdrops and is reproducible on any machine: border trim 61% mean IoU (7/14 usable), previous cutout 78% (10/14), silhouette pass 85% (12/14), with the decisive gains on a second object in shot (44% to 97%) and a crowded rail (37% to 97%). Both intake paths now share the pass, each keeping its existing fallbacks, and an ambiguous photo is declined rather than cropped to a guess. Writing the tests first surfaced two real defects in the new code — sharp orders `joinChannel` after `extract`, which silently discarded both the transparency and the crop — and a strongly patterned backdrop remains a recorded limitation rather than a fixed case.

## Phase 26 — Recognition that does not silently discard the garment (2026-08-30)

- [#97](https://github.com/manof1color/racked-wardrobe-intelligence/pull/97) fixes a reported failure where a single pair of shorts, photographed alone and clearly visible, came back as "No distinct clothing pieces were detected". The cause was not the model's vision but Racked's own parsing: the detection prompt asked for 0-1 fractional bounding boxes and the parser accepted nothing else, while an unreadable box discarded the entire detection. A probe of the seven conventions vision models actually emit showed six of them — percentages, source pixels, corner arrays, left/top/right/bottom keys, and a missing or null box — being silently dropped even when the garment was correctly identified, named, and classified. Generic category words such as "clothing" or "apparel" deleted the piece as well. Bounding-box reading now lives in `lib/detection-bounds.ts`, accepts every convention, rescales percentages and pixels using the real image dimensions, and falls back to the whole frame rather than discarding a garment the model named; an unrecognized category survives as an explicitly unknown piece for the person to correct. When detection genuinely returns nothing, the route no longer dead-ends with an HTTP 422 blaming the photograph: it offers the photo as one manual-review candidate with zero confidence and no invented attributes, which the intake UI labels "needs your label". The prompt now states its coordinate convention explicitly and tells the model that a photo of exactly one garment is normal. A separate latent defect surfaced during the work: `AI_HANGER_MODEL` was read in code but missing from the Amplify runtime allowlist, so setting it in production had always been silently ignored; it and the new `AI_LOOK_DETECTION_MODEL` are now registered, and a test fails if any `AI_*` override is ever read without reaching production. Ten tests were added, and the two guards were each confirmed non-vacuous by reintroducing the defect they cover.

## Phase 33 — Typeable garment type and review of the footwear work (2026-09-13)

- [#115](https://github.com/manof1color/racked-wardrobe-intelligence/pull/115): recognition fills the intake **Type** field when it can. When it cannot — low confidence, an unknown category, a fallback subtype, or a manual-review stand-in — the field is highlighted and a short note appears beneath it, never over the photograph. Type is now free text with suggestions rather than a fixed list. Typed words resolve onto the controlled taxonomy (exact phrase first, then the longest whole-word phrase), may settle an unknown category, and are otherwise kept verbatim as a bounded `customType` beside the category's `other-*` subtype, so outfit ranking and Community filters still receive a controlled value. The server stores that label only beside a fallback subtype, strips control characters, caps it at 60 characters, and never lets it touch verified identity. Closet displays it, and a piece whose category is still unknown can no longer be saved.
- Review of the preceding Codex work (#113 and the `js-yaml` advisory response): the gate was green and the footwear reference well tested and brand-safe. One change, however, had edited `components/look-scan-uploader.tsx`, a component no page rendered, and a detection test asserted against it — confidence about UI nobody could see. The component and its 36 orphaned CSS rules are removed and the test now targets the rendered intake.
- Stated rather than implied: no model was trained. This environment has no Python ML toolchain or GPU, and Bedrock fine-tuning would need a customisation job, dedicated serving capacity, and a commercially licensed labelled dataset. The whole-look prompt was also not lengthened, because that path already runs against the 18-second deadline introduced after mobile 504s. The suite contains 339 tests.

## Phase 34 — Whole-piece previews and a pinned iPhone tab bar (2026-09-14)

- [#116](https://github.com/manof1color/racked-wardrobe-intelligence/pull/116): a phone test after #115 showed correctly recognised pieces looking mis-cropped: a dress displayed only from belt to thigh, a pendant only in part. The saved crops were not the problem — scan and Closet previews filled their tiles with `object-fit: cover`, which shows only the middle band of a tall garment. Previews now show the crop contained on a plain ground, taller on phones, and clear of the category label and wear button, so pieces already in a wardrobe are fixed without a rescan. Detection crops also keep an 8% margin (previously 4%) so a tight box cannot clip a hem or a chain. The scan tile needed one more fix: its grid row was sized by its content, so the image's `height: 100%` resolved to nothing and a tall photo measured 729px inside a 300px tile; a definite track now lets it be contained. Regression tests forbid `cover` in any intake or Closet photo rule and lock that track.
- The same test showed the bottom tab bar and the Hanger button drawn part-way up the Closet with garments beneath them. In an iPhone home-screen app the layout viewport that `position: fixed` is measured against can stay out of step with the visible screen after the keyboard closes. The signed-in shell now measures that drift with the Visual Viewport API, moves both controls down by exactly the gap, asks the browser to re-synchronise once typing ends, and hides both controls while a text field is focused on a touch device. The correction is unit-tested; it has not yet been re-checked on a physical iPhone.
- A stacked-bracelets piece displayed nearly the whole outfit. Its box most likely spanned both wrists or was too small to read, so it fell back to the whole frame; that is recorded as an open recognition case rather than hidden. The suite contains 347 tests.

## Phase 35 — Bounded crop only in live intake (2026-09-14)

- [#117](https://github.com/manof1color/racked-wardrobe-intelligence/pull/117): a phone scan recognised white trousers correctly, but the background-removal pass kept the hand holding them and erased most of the trousers. It was the same failure as the earlier white sneaker: when a garment is close in colour to its surroundings, colour similarity has nothing to separate, and the existing visible-subject and one-region guards did not catch it. Rather than add a third heuristic before publishing, live intake now stores every detected piece as its bounded crop — the recognised box plus an 8% margin, zoomed to the garment, with the photograph intact. The isolation and edge passes, their guards, and the crop benchmark stay in the repository as measured research and as the baseline a learned segmenter must beat. Pieces already saved as shredded cut-outs need rescanning. An open Add sheet also now hides the tab bar and Hanger button instead of letting them show beneath its edge. The suite contains 350 tests.

## Phase 36 — Garment and account deletion (2026-09-16)

- The streamline audit found two launch blockers: a garment could not be deleted, so a bad scan stayed in the closet, and there was no account deletion, which Apple Guideline 5.1.1(v) and Google Play both require. `/privacy` had also promised a deletion workflow that no code implemented. Garment deletion now updates saved outfits (an emptied one is deleted), removes the photo from the owner's own Community posts, deletes the wear events it added under brand products, and deletes its photos — the shared scan photo only with the last piece cut from it. Consumer account deletion requires the current password and the typed word DELETE; it removes posts, wear events, every referenced photo, and every record with the profile last, then clears the session. Both are ordered so an interrupted deletion finishes on retry, and neither can reach storage outside the account's own prefix. The runtime role cannot list the bucket, so the template adds `s3:ListBucket` scoped to `wardrobe/`; until the stack is updated, never-saved scan photos are not swept and the gap is logged. Brand account deletion, which must first unlink consumer garments verified against the brand's products, is specified in the ChatGPT work order rather than rushed. A plain-language pilot `/terms` page, stating it has not had legal review, is linked beside Privacy. An existing test that reads the outfit-deletion code to prove it never erases wear history was kept intact by placing the new code outside the span it reads. The suite contains 365 tests.
